# 03 · 评测设计

> **评测是这个项目的脊柱。** 没有它，后面所有「优化」都是自嗨。

---

## 1. 评测对象

| 层 | 评什么 | 怎么评 |
|---|---|---|
| 分诊 | 类别对不对 | 宏 F1、混淆矩阵 |
| 分诊 | 知不知道自己不确定 | ECE、可靠性图 |
| 回复 | 能不能用 | rubric + 人工抽检 |
| 系统 | 划不划算 | 每千单成本、P95 延迟 |
| 系统 | 稳不稳 | 峰值成功率、兜底率 |

---

## 2. 标注手册（先写，再标）

> 类别定义含糊，是评测不可信的第一大原因。

### 2.1 类别（示例，待定）

| 类别 | 定义 | 边界（不算） | 典型例子 |
|---|---|---|---|
| `退款` | 用户明确要求退款/退货 | 只是抱怨质量但没提退款 | 「买了三天能退吗」 |
| `物流` | 查询/投诉配送进度 | 已签收后的售后问题 | 「一直没发货」 |
| `其他` | 以上都不是 | — | 「你们公司地址在哪」 |

### 2.2 标注规则

1. **只看正文**，不看历史（避免信息泄漏）
2. 一句话含两个意图 → 标**主要诉求**，并在 `notes` 里记
3. 拿不准 → 标 `其他`，**禁止猜**
4. 每 50 条做一次双人复核（自己隔一天再看一遍）

### 2.3 一致性

- 抽样 30 条，自己标两遍，算 Cohen's kappa
- 目标 κ ≥ 0.8；低于 0.7 说明类别定义有问题，回去改手册

## 3. Golden set

### 3.1 三条来源

| 来源 | 放哪 | 可否入库 | 作用 |
|---|---|---|---|
| 公开数据集 | `data/synthetic/` | ✅ | 跑通链路 |
| LLM 合成 | `data/synthetic/` | ✅ | 造长尾、造歧义 |
| 公司脱敏 | `data/private/` | ❌ **永不入库** | 最终校准 |

### 3.2 规模

| 用途 | 条数 | 说明 |
|---|---|---|
| 冒烟 | 30 | 开发时快速迭代 |
| 回归 | 150 | 每次改动必跑 |
| 定版 | 300+ | 阶段末、对外报告用 |

> 300 条足够讲清结论；3000 条不会让结论更可信，只会让你更晚交付。

### 3.3 冻结

- `test` 切分**只读**，写完就打 hash 记进 `eval/golden/MANIFEST.json`
- 每次评测记录：数据 hash + 模型名 + 参数
- **改 golden set 必须写 ADR**，说明为什么改、改完指标怎么变

## 4. 指标

### 4.1 分诊

```python
macro_f1 = mean(f1_per_class)
```

- 类别不平衡时**永远看宏 F1**，不看准确率
- 混淆矩阵必出，重点看「哪两类最容易混」
- 每类给 P / R / F1，长尾类单独标红

### 4.2 置信度校准（最容易被忽略，最能体现水平）

模型说 0.9，就应该有 90% 是对的。不对，就不能拿它做路由。

```
ECE = Σ (n_b / N) × |acc_b − conf_b|
```

- 分 10 个桶，画可靠性图
- 目标 ECE ≤ 0.05
- 校准手段：temperature scaling（在 val 上拟合，**不能碰 test**）

### 4.3 回复质量（rubric）

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 正确性 | 事实错 | 大体对 | 完全对 |
| 可执行性 | 用户还得再问 | 部分可执行 | 直接可执行 |
| 语气 | 冒犯/机械 | 中性 | 得体 |
| 合规 | 越权承诺 | 含糊 | 有边界 |

- 人工抽 50 条定标
- LLM judge 先和人工对齐（一致率 ≥ 80%）再大规模用
- **judge 的 prompt 和被评模型分开**，避免自评

## 5. 错误归因框架

每条 badcase 必须落到一个桶里，否则不许改：

| 桶 | 判据 | 典型修法 |
|---|---|---|
| **数据** | 标签错 / 文本脏 / 重复 | 清洗、重标 |
| **定义** | 两类边界模糊 | 改手册，不改模型 |
| **覆盖** | 训练集没有这类 | 补数据 |
| **模型** | 数据没问题，就是学不会 | 换尺寸 / 调 LoRA |
| **提示** | few-shot 例子误导 | 改 prompt |
| **系统** | 路由/兜底策略错 | 改阈值 |

> 报告里永远先给桶的分布，再给总数。**分布比数字有用。**

---

## 6. 防泄漏清单

- [ ] 按 `created_at` 时间切分（train 早 → test 晚）
- [ ] 按 `id` 去重
- [ ] near-dup 检测（MinHash 或简单 n-gram Jaccard > 0.9 判重）
- [ ] 合成数据不得由测试集改写而来
- [ ] 校准参数只在 val 上拟合
- [ ] few-shot 例子不得取自 test
