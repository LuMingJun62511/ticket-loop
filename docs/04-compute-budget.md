## 1. 训练显存：五项相加

```
显存 ≈ 权重 + 优化器状态 + 梯度 + 激活 + 临时/碎片
```

### 1.1 各项怎么算

| 项 | 公式 | 全参微调 | LoRA |
|---|---|---|---|
| 权重 | `N × bytes` | 全量 | 全量（冻结，不存梯度） |
| 梯度 | `N × bytes` | 全量 | ≈ 0（只存 adapter） |
| 优化器 | `N × 8`（AdamW fp32 m+v） | 全量 | 只算 adapter |
| 激活 | 与 `bs × seq × layers` 成正比 | 大 | 大（一样） |
| 临时 | 通常预留 0.5–1 GB | | |

### 1.2 代入 0.6B

Qwen3-0.6B 参考配置：`hidden=1024, layers=28, heads=16, kv_heads=8, head_dim=128`

| 项 | 计算 | 结果 |
|---|---|---|
| 权重（fp16） | 0.6e9 × 2 B | **1.20 GB** |
| 权重（4bit） | 0.6e9 × 0.5 B | **0.30 GB** |
| LoRA 参数 | r=16，约 8–12 M | 20–30 MB |
| 优化器（仅 LoRA） | 10e6 × 8 B | 80 MB |
| 激活（bs=8, seq=512, 开 grad ckpt） | 经验值 | **0.8–1.5 GB** |
| 激活（同上，关 grad ckpt） | 经验值 | 3–5 GB |
| 碎片/临时 | | 0.5 GB |
| **合计（LoRA + ckpt）** | | **≈ 2.5–3.5 GB** ✅ |
| **合计（全参 fp16）** | 1.2 + 1.2 + 4.8 + 激活 | **> 8 GB** ❌ |

**结论**：6 GB 上**全参微调 0.6B 不可行**，**LoRA 可行**。这就是为什么要记这一笔账。

### 1.3 参数怎么调（显存不够时按顺序动）

1. 开梯度检查点（用时间换显存，约慢 20–30%）
2. 降 `bs`，升 `grad_accum`（总 batch 不变）
3. 降 `seq_len`（先看数据长度分布，别拍脑袋）
4. 上 4bit QLoRA（再省约 0.9 GB）
5. 降 LoRA rank / 减少 target module

## 2. 训练时间：FLOPs 估算

### 2.1 公式

```
单步 FLOPs ≈ 6 × N × tokens_per_step        （前向 2 + 反向 4）
tokens_per_step = bs × seq × grad_accum
总 tokens = 样本数 × 平均长度 × epochs
总 FLOPs = 6 × N × 总 tokens
时间(s) = 总 FLOPs / (N_gpu × 单卡有效 FLOPs)
有效 FLOPs = 峰值 FLOPs × 利用率（经验 0.3–0.5）
```

### 2.2 本机代入

| 参数 | 取值 |
|---|---|
| N | 0.6e9（LoRA 也按全模型前反向算） |
| 3060 Laptop fp16（Tensor Core） | 峰值 ≈ 25 TFLOPS（稀疏口径，实际按 12 算） |
| 利用率 | 0.4 → 有效 ≈ **5 TFLOPS** |
| 训练集 | 4000 条 × 256 token = 1.02 M token |
| epochs | 3 |
| 总 tokens | 3.07 M |

```
时间 = 6 × 0.6e9 × 3.07e6 / 5e12
     = 1.1e16 / 5e12
     ≈ 2210 s ≈ 37 分钟
```

> **这就是「先算后跑」的意义**：跑之前你就知道大概是半小时，
> 跑了两小时说明配置或估算有问题，立刻停下来查，而不是干等。

### 2.3 卡的估算（通用写法）

```
需要的卡数 = ceil(总 FLOPs / (目标时间 × 单卡有效 FLOPs))
```

本机答案：`ceil(1.1e16 / (1800 × 5e12)) = 2` → 2 张 3060 级别。
所以单机单卡 37 分钟、双卡理论 18 分钟，**但通信和 batch 效率会让它变成 22–25 分钟**。
→ 记住这句话：**小模型小数据下，加卡的边际收益远低于线性。**

## 3. 推理：并发怎么算

### 3.1 三组数字，别混

| 概念 | 定义 | 怎么测 |
|---|---|---|
| **并发数** | 同时在飞的请求数 | 压测脚本的参数 |
| **QPS** | 每秒完成请求数 | `完成数 / 时长` |
| **吞吐** | 每秒 token 数 | `总输出 token / 时长` |

关系：`QPS ≈ 并发数 / 平均延迟`（Little 定律）

### 3.2 KV cache 显存（决定能开多大 batch）

```
KV bytes = 2 × layers × kv_heads × head_dim × seq × bs × bytes_per_elem
```

Qwen3-0.6B，seq=512，fp16：

```
2 × 28 × 8 × 128 × 512 × 2 B = 58.7 MB / 每条序列
```

| batch | KV | + 权重 1.2G(q8 0.6G) | 合计 |
|---|---|---|---|
| 8 | 0.47 G | 1.2 G | 1.7 G ✅ |
| 16 | 0.94 G | 1.2 G | 2.1 G ✅ |
| 32 | 1.88 G | 1.2 G | 3.1 G ✅ |
| 64 | 3.76 G | 1.2 G | 5.0 G ⚠️ |

**结论**：6 GB 上 0.6B 的 batch 上限约 32–48，再往上就要 OOM 或 offload。
这就是压测时会看到的「拐点」来源之一。

### 3.3 分诊任务的特殊性

- 输出极短（1 个标签，3–5 token）→ **prefill 主导，decode 很轻**
- 所以吞吐主要看输入长度，不看生成长度
- 优化优先级：**批处理 > 量化 > 换模型**

## 4. 数据切分

### 4.1 按时间切（不是随机切）

```
train : 最早 70%
val   : 中间 15%
test  : 最近 15%   ← 只读，冻结
```

为什么：客服数据的分布随时间漂移。随机切会让模型「偷看未来」，
测出来的分数比线上高，**这是最常见的自欺**。

### 4.2 分层抽样

- 每个 split 内，每类至少 `max(20, 5%)` 条
- 长尾类不足时：train 里上采样，**val/test 绝不上采样**
- 记录每类的分布表，写进报告

### 4.3 边界处理

- 同一用户同一天的连续工单 → 只保留一条，避免近重复
- 同一模板批量生成的工单 → 只进 train，不进 test
- 时间边界上的工单：按 `created_at` 精确到天，避免跨集合

## 5. 成本模型

```
每千单成本 = 1000 × (输入 token × 单价_in + 输出 token × 单价_out)
```

三个臂对比：

| 臂 | 输入 token | 输出 token | 单价 | 千单成本 |
|---|---|---|---|---|
| 大模型 API | ~300 | ~50 | 待填 | 待填 |
| 0.6B 本地 | ~300 | ~5 | 电费/摊销 | ≈ 0 |
| 路由 | 加权 | 加权 | — | 待填 |

> **本地不是真的免费**：要摊 GPU 折旧、电费、运维人力。
> 报告里必须写清「按什么口径算的」，否则数字经不起追问。
