## P1 · 数据 + eval harness（3–4 晚）

### 做什么

1. `data/schema.md` 已有；实现 `ingest → clean → split`
2. 数据来源（三选一，允许混）：
   - 公开客服意图数据集（少量，够跑通）
   - 用 DeepSeek 合成 200–500 条（2–3 类，带长尾噪声）
   - 公司脱敏样本（只放 `data/private/`，永不入库）
3. 实现 `eval/`：
   - 宏 F1、每类 P/R/F1、混淆矩阵
   - 置信度校准（ECE + 可靠性图）
   - 错误归因清单（哪类错、错在数据还是模型）
4. 两条 baseline：零样本 API、few-shot API

### 验收

```powershell
uv run python scripts/run_eval.py --model api --mode zero-shot
uv run python scripts/run_eval.py --model api --mode few-shot
```

输出：`eval/reports/{timestamp}.json` + 一个人类可读的 `summary.md`。

### 风险

- 合成数据太干净 → 故意加 10% 噪声、5% 长尾、3% 歧义样本
- 类别定义含糊 → 先写 **标注手册**（`docs/03-eval-design.md` 第 2 节）

## P2 · 算力账本 + LoRA（3–4 晚）

### 做什么

1. **先算后跑**：用 `docs/04-compute-budget.md` 的公式估值
   - 权重 / 优化器 / 激活 / KV 各占多少
   - 单步 token 数 = bs × seq × grad_accum
   - 总 token = 样本数 × 平均长度 × epochs
   - 预计时间 = 总 token × 6N / (有效 FLOPs × 利用率)
2. 实跑 Qwen3-0.6B + LoRA（r=16，target = q/k/v/o + MLP）
3. 记录：显存峰值、tokens/s、每 epoch 时间
4. **对比估算与实测**，把偏差写进报告

### 验收

| 项 | 要求 |
|---|---|
| 估算表 | 有公式、有代入、有结论 |
| 实测 | 训练完成，adapter 落盘 |
| 偏差 | ≤ 30%，超出要解释（通常是激活或碎片） |
| 消融 | 至少 2 组：r=8 vs r=16，或 开/关梯度检查点 |

## P3 · 服务 + 压测（3–4 晚）

### 做什么

1. Ollama 起 0.6B（GGUF，q4/q8 各一份）
2. 实现 `Endpoint` 三实现：`LocalOllama` / `RemoteAPI` / `Mock`
3. 压测脚本 `scripts/loadtest.py`：
   - 并发扫描：1 / 4 / 8 / 16 / 32
   - 记录 QPS、P50/P95/P99、显存、错误率
4. 出图：QPS–延迟曲线，找到**拐点**

### 验收

- 一张曲线图，标出「线性区 / 拐点 / 崩溃点」
- 一句话结论：「这台机器在 0.6B q4 下，稳定 QPS ≈ ___」

---

## P4 · 路由 + 兜底（3–4 晚）

### 做什么

1. 小模型输出置信度（logprob 或自洽投票）
2. 扫阈值：0.5 → 0.95，画「成本 vs F1」曲线
3. 选一个工作点，写清理由（业务上哪类错更贵）
4. 兜底：低置信 + 特定类别 → 人工队列，记录比例

### 验收

| 指标 | 要求 |
|---|---|
| 成本 | 相比全大模型降 ≥ 40% |
| 质量 | 宏 F1 掉 ≤ 2% |
| 兜底率 | 给出比例与成本换算 |

---

## P5 · 观测 + 漂移（3–4 晚）

### 做什么

1. 自写 trace（JSONL）：ticket_id / 每步模型 / tokens / 延迟 / 成本 / 结果
2. 一个 `report.py` 把 trace 聚合成日报
3. **漂移演练**：人为把 20% 测试样本换成「新类别」文本
   - 观察：置信度分布变化、兜底率变化、F1 变化
   - 设计一个**不需要标注**的报警信号（如：平均置信度下降 + 兜底率上升）

### 验收

- 一份漂移报告：注入前后对比 + 报警触发时间
- 一句话：「如果线上出现新舆情，我靠 ___ 在 ___ 小时内发现」
